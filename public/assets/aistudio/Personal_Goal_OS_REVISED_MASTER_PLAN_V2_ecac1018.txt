============================================================
1. THE CORRECT CORE FLOW
============================================================

CAPTURE → CLARIFY → CLASSIFY → DECIDE → PLAN → EXECUTE → REVIEW → ADJUST

1. CAPTURE (Brain Dump / Universal Inbox)
   - User can instantly type or paste anything: thought, wish, worry, idea,
     reminder, task, opportunity, question, habit idea, or random note.
   - Quick capture should take about 5 seconds and require only the text.
   - No category, deadline, life area, goal, priority, or explanation is required
     during capture. Optional voice capture can be considered later.
   - Save first; organize later. The system must never interrupt capture with
     a questionnaire.
   - Capture is not a promise. Saving a thought does not create an obligation.

2. CLARIFY (processing queue)
   - When the user has time, process one item at a time.
   - Show the original text and offer concise suggested interpretations.
   - Ask a question only if it materially helps decide what the item means.
   - Let the user edit the wording, split one item into several items, merge
     duplicates, defer processing, archive, or delete.
   - AI suggestions must be labelled as suggestions. No automatic promotion,
     commitment, deletion, or deadline assignment.

3. CLASSIFY (item types)
   Each inbox item can be classified as one of:
   A. Next action / task — a specific action the user can actually do.
   B. Goal candidate — a desired outcome that may deserve sustained effort.
   C. Project — a multi-step piece of work with a finish line, often supporting
      a goal but sometimes useful on its own.
   D. Routine / habit candidate — a repeatable behaviour or process.
   E. Reference / knowledge — information to keep, not an action.
   F. Idea / experiment — something to explore without committing.
   G. Someday / maybe — a possibility intentionally not active now.
   H. Concern / question — something to understand, resolve, or revisit.
   I. Waiting for / delegated — something dependent on another person/event.
   J. Trash / duplicate — only after the user confirms.
   These types are not all equal. In particular, “Goal candidate” is not yet an
   active goal, and “Idea” is not automatically a task.

4. DECIDE (explicit user choice)
   The user chooses the next state: act now, schedule, make a goal candidate,
   keep as reference, put in Someday/Maybe, wait, archive, or discard.
   If unsure, leave it in the inbox or defer it. There is no penalty for
   uncertainty and no requirement to process the entire inbox at once.

5. PLAN
   Only accepted active goals proceed into structured planning:
   Goal → Milestones → Project(s), where useful → Next actions / tasks →
   optional calendar schedule.
   Repeatable behaviours can be linked as habits/routines. Not every goal needs
   a project, not every task needs a goal, and not every goal needs a deadline.
   The system should not force unnecessary hierarchy.

6. EXECUTE
   The Today view shows a manageable set of actions and routines. The user can
   complete, reschedule, shrink, pause, or cancel an action. The system should
   optimize for useful execution, not for filling the calendar.

7. REVIEW & ADJUST
   Daily review handles loose ends briefly. Weekly review checks whether active
   goals still matter, progress is realistic, and the plan fits actual life.
   Reviews change the plan, not the user's worth. Gaps are handled with a
   low-friction restart, not guilt or streak punishment.

2. GOAL QUALITY GATE — A THOUGHT MUST EARN GOAL STATUS
============================================================

When the user selects “Consider as Goal”, create a Goal Candidate, not an
active goal. Then guide the user through a short, adaptive review. Do not ask
every question if the answers are already clear.

Core questions:
1. Desired outcome: What do you want to be different or true?
2. Personal reason: Why does this matter to you personally?
3. Ownership: Is this genuinely wanted by you, or mostly comparison, pressure,
   fear of missing out, or someone else's expectation? The system must invite
   reflection, not claim to know the user's “true” motives.
4. Evidence: How would you recognize meaningful progress or completion?
5. Control: Which part is within your influence, and what depends on others?
6. Cost/trade-off: What time, money, energy, or attention will this consume?
   What might need to be reduced or paused?
7. Capacity: What is a realistic minimum next action and when could it fit?
8. Horizon: Is this ongoing, direction-based, or a time-bound outcome?
9. Classification check: Is this actually a goal, a project, one task, a habit,
   a wish, a problem to solve, or information to keep?

Goal acceptance outcomes:
- ACCEPT AS ACTIVE GOAL: user confirms it matters and accepts the trade-offs.
- REFINE: outcome is vague, oversized, or mixed with several different goals.
- CONVERT TO PROJECT/TASK/HABIT: the item was misclassified as a goal.
- SOMEDAY / MAYBE: worth keeping, but not a current commitment.
- KEEP AS IDEA / REFERENCE: useful without action now.
- DECLINE / ARCHIVE: user decides it is not worth pursuing.

A goal should normally have:
- A clear outcome or direction in the user's own words.
- A recorded personal reason (can be brief).
- A life area (editable; not a rigid taxonomy).
- A goal type: time-bound outcome or ongoing direction/system.
- A status: candidate, active, paused, completed, abandoned/archived.
- A review date or review cadence, even if it has no deadline.
- A plausible next action OR an explicit note that the next step is still unclear.
- Optional evidence/measure of progress; do not force a numeric metric for every
  personal, relational, or exploratory goal.

Important safeguards:
- The user always makes the final decision. AI cannot approve a goal by itself.
- Never auto-create a deadline, daily commitment, habit, or task just because
  the user wrote a thought.
- A large or expensive goal may show a gentle “sleep on it / revisit tomorrow”
  suggestion, but never impose a blocking cooldown.
- Active-goal count warning is advisory, not a hard limit. If too many goals
  are active, suggest choosing, pausing, or reducing scope; do not shame/block.
- A goal can be valid even if the user cannot currently commit time to it; it
  can stay in Someday/Maybe without being lost.
- The AI must not diagnose motives or use spiritual/philosophical concepts as
  scientific facts. Self-inquiry prompts are optional reflection aids.

3. UNIVERSAL INBOX SCREEN — REQUIRED BEHAVIOUR
============================================================

Quick capture:
- A persistent “+ Brain Dump” action should be available from the main app.
- One multiline text field; Save/Enter saves the raw item to Inbox. On mobile,
  use a clear Save button and preserve accidental line breaks.
- Optional capture source and timestamp may be stored automatically.
- After save, show a small confirmation and allow immediate next capture.
- No required category or extra helper text that slows down capture.

Inbox processing view:
- Tabs/filters: Unprocessed | Waiting | Someday/Maybe | Processed/Archived.
- Default queue shows unprocessed items in capture order, with optional sort.
- Each card offers: Process, Split, Merge/duplicate, Defer, Archive, Delete.
- Processing starts with suggested category choices, not a forced AI chat.
- User can manually choose any category even if AI recommends another.
- “Not sure yet” is a valid outcome.
- Processed items retain a link to the resulting task/goal/project/habit where
  applicable, so the origin and decision history can be traced.
- Deletion is reversible where practical (trash/undo); do not permanently
  delete by an ambiguous one-tap gesture.
- Show a gentle count of old inbox items only as information, not a guilt alert.

4. DATA MODEL CHANGES REQUIRED
============================================================

The original plan already has inbox_items, goals, milestones, tasks, life_areas,
routines, reviews, and daily execution tables. Keep that modular base, but
extend the Brain Dump → decision → goal candidate pathway before implementation.

Inbox item fields to consider:
- id, user_id, content, created_at, updated_at
- status: new, processing, waiting, processed, someday, archived, trash
- item_type: unknown, task, goal_candidate, project, habit_candidate,
  reference, idea, concern, waiting_for, duplicate
- source (manual initially; future sources optional)
- processed_at, archived_at
- decision_note (optional short reason)
- linked entity type + linked entity id, or a safer explicit link table if
  multiple outputs are possible
- AI suggestion metadata only if useful; do not store private chain-of-thought.

Goal fields to review/add:
- status must distinguish candidate from active (e.g. candidate, active, paused,
  completed, abandoned/archived).
- goal_type: outcome / ongoing_direction.
- desired_outcome, purpose_reason, evidence_of_progress (optional).
- tradeoffs/constraints (optional, concise).
- review_date or review cadence.
- origin_inbox_item_id (nullable provenance link).
- Do not require deadline; support no deadline for ongoing goals.

Relationships:
- One inbox item may produce zero, one, or several entities after splitting.
- One task may be standalone; linking to a goal/milestone is optional.
- A goal can have milestones, but a simple goal can go directly to tasks.
- A project is distinct from a milestone: milestone is a meaningful checkpoint;
  project is a bounded body of work. Avoid treating these as interchangeable.
- A habit/routine is a repeatable process and can optionally support a goal.
- All owned records retain strict user ownership, RLS, and appropriate foreign
  keys. Never trust client-provided user_id.

Before changing SQL:
1. Review the current original migration and all references.
2. Design the revised schema and constraints.
3. Check migration/backward-compatibility and RLS test cases.
4. Only then create a migration; do not casually rewrite live data.

5. NAVIGATION AND SCREEN ORDER
============================================================

Keep the mobile-first bottom navigation simple. Recommended primary navigation:
Today | Brain Dump / Inbox | Tasks | Goals | Settings

- “Brain Dump” should be visually easy to reach from every screen.
- Brain Dump capture must be faster than creating a task or goal manually.
- Inbox processing belongs inside the Inbox screen; it does not need a separate
  permanent navigation tab unless testing shows it is confusing.
- Goal Candidate review can be a guided sheet/screen opened from Inbox.
- Goals screen should show active goals by life area, with candidate/someday
  lists accessible but not mixed into the active commitment list.
- Today remains focused on current execution, not a giant list of all life
  ambitions. The user can choose to reveal other information.

6. REVISED BUILD ORDER — BRAIN DUMP FIRST
============================================================

Do not start with reminders or routines. The information pipeline is foundational.
Recommended phase order:

P0 — Decisions & repository setup
  Confirm whether to use the existing AbhiOs repository/Supabase project or
  create a dedicated private repo and fresh Supabase project. Document the
  decision, source-of-truth docs, deployment, and rollback plan.
  Acceptance: project target and ownership are explicit; no production data is
  modified unexpectedly.

P1 — Data model & security design
  Design inbox statuses/types, goal candidates, active-goal gate, provenance,
  entity relationships, RLS, and migration strategy.
  Acceptance: schema review and ownership/RLS tests pass before UI is built.

P2 — App shell + authentication + Brain Dump capture
  Build the mobile shell, login, quick capture, Inbox list, edit, archive/trash,
  and reliable save/loading/error states.
  Acceptance: capture a thought in a few seconds on phone; it persists after
  reload; no category is required; unauthenticated access is blocked.

P3 — Inbox processing & classification
  Add manual triage, split, merge/duplicate handling, defer, Someday/Maybe,
  reference, waiting-for, and traceable conversion links.
  AI is not required for this phase.
  Acceptance: every item can be safely left undecided or assigned a user-chosen
  type without accidentally becoming an active goal/task.

P4 — Goal Candidate & quality gate
  Build the adaptive goal clarification flow and explicit user approval.
  Start with deterministic questions/rules; AI can later suggest concise
  questions, rephrasing, and classification.
  Acceptance: a candidate cannot become active without user confirmation;
  goal vs task/project/habit/reference outcomes work; no auto-deadlines.

P5 — Goals, life areas, milestones, projects, and next actions
  Implement accepted active goals and the lightest useful breakdown. Avoid
  mandatory hierarchy where it adds no value.
  Acceptance: a user can create a valid goal, pause it, link a next action, and
  trace it back to the originating inbox item.

P6 — Tasks, calendar/scheduling, Today execution
  Add task states, schedule/reschedule/split/cancel, day plan, main priority,
  minimum viable day, and workload-aware recommendations.
  Acceptance: tasks appear on the intended local date; timezone/rollover tests
  pass; recommendations are explainable and editable.

P7 — Routines & habit systems
  Add daily routines, water tracking, duty/off-day context, and repeatable
  actions. Keep habit completion separate from goal achievement.
  Acceptance: routines work without a linked goal; skipped routines do not
  create guilt or corrupt progress.

P8 — Daily and weekly review + re-entry
  Add brief daily close-out, weekly goal review, plan adjustments, and a gentle
  return after gaps.
  Acceptance: overdue tasks can be shrunk/rescheduled/cancelled/archived; review
  never requires the user to complete every missed task.

P9 — Notifications/reminder engine
  Only after the core workflow is stable: permissions, push, quiet hours,
  dedupe, caps, security, cron, and test notifications.
  Acceptance: reminders respect preferences and do not duplicate or send in
  quiet hours; explain that browser/OS delivery is not guaranteed to the minute.

P10 — Export/import, security hardening, accessibility, polish
  Backup/restore validation, error states, mobile touch targets, performance,
  audit, deployment smoke tests.
  Acceptance: export and restore are tested on a clean test environment; RLS
  and security checks pass.

P11 — Optional AI assistance
  Add server-side, provider-agnostic AI only for suggestions: classification,
  clarification, goal refinement, goal breakdown, task splitting, and planning.
  AI outputs must be validated against a strict schema; user approves changes.
  Core features must work without AI. Do not store hidden reasoning; store only
  user-approved decisions and concise explanations.

P12 — Future modules
  Optional voice capture, knowledge links, finance/study/fitness modules, focus
  timer, offline write queue, and analytics only when the core system is useful.
  Do not add these to the initial scope by default.

============================================================
7. PRODUCT PRINCIPLES / WHAT NOT TO DO
============================================================

- Capture first, organize later.
- A thought is not a commitment.
- A goal candidate is not an active goal.
- No AI action that creates, changes, deletes, schedules, or commits something
  without the user's explicit confirmation.
- No forced numeric score for a person's life, no “Life Score”, and no streak
  punishment.
- Do not turn every life area into a goal or every goal into daily tasks.
- Do not use active-goal count as a strict limit.
- Do not overwhelm the Today screen with all inbox items, distant deadlines,
  or long-term outcomes.
- Avoid excessive reminders and repetitive review forms.
- Keep AI optional and the core product useful without AI.
- Separate evidence-backed behavioural principles from popular frameworks,
  metaphors, and spiritual reflection prompts.
- Modular boundaries must be real: screen/UI, data access, pure logic/rules, and
  optional AI integration stay separated.
- Keep an audit trail for important user-approved transitions without collecting
  unnecessary sensitive data.

  |  Push service     | <---------------------------------------------+  Vercel /api       |
  |  (Google FCM)     |                                               |  (Node functions)  |
  +-------------------+                                               +---------+----------+
                                                                                ^
                                          Supabase pg_cron + pg_net ------------+

3.2 Data flow rules
  - CRUD (tasks, goals, routines...): browser -> Supabase directly. Security RLS se.
  - Server code (service_role) SIRF: reminder tick, push subscribe/send, signed
    done-link, AI proxy. Baaki sab client se.
  - service_role key browser me kabhi nahi.
  - /api responses cache nahi hote. Service worker /api ko kabhi cache nahi karta.

3.3 Why this design (short)
  - Kam serverless code = kam bug = AI-generated code audit karna aasan.
  - RLS database level par security deta hai, frontend bug se data leak nahi hota.
  - Reminder engine server par hai kyunki browser band ho to bhi push chahiye.

5. DATABASE - FULL SQL
============================================================

Supabase SQL Editor me chalao. Postgres 15+ assume kiya gaya hai (Supabase me hota hai).

----- supabase/migrations/0001_core.sql -----

-- Helper: updated_at trigger
create or replace function public.touch_updated_at() returns trigger
language plpgsql as $$
begin new.updated_at = now(); return new; end $$;

-- 1) Settings (ek row per user)
create table public.user_settings (
  user_id uuid primary key default auth.uid() references auth.users(id) on delete cascade,
  timezone text not null default 'Asia/Kolkata',
  wake_time time not null default '06:30',
  quiet_start time not null default '23:00',
  quiet_end time not null default '06:00',
  day_rollover_hour int not null default 4 check (day_rollover_hour between 0 and 8),
  daily_workload_minutes int not null default 120 check (daily_workload_minutes between 15 and 720),
  duty_prompt_time time not null default '06:45',
  review_time time not null default '21:30',
  max_reminders_per_day int not null default 8 check (max_reminders_per_day between 1 and 30),
  push_enabled boolean not null default true,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

-- 2) Life areas
create table public.life_areas (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users(id) on delete cascade,
  name text not null check (char_length(name) between 1 and 80),
  description text,
  status text not null default 'active' check (status in ('active','archived')),
  sort_order int not null default 0,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (id, user_id)
);

-- 3) Goals
create table public.goals (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users(id) on delete cascade,
  life_area_id uuid not null,
  title text not null check (char_length(title) between 1 and 160),
  reason text,
  status text not null default 'active' check (status in ('active','paused','done','archived')),
  target_date date,
  review_date date,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (id, user_id),
  foreign key (life_area_id, user_id) references public.life_areas(id, user_id) on delete restrict
);

-- 4) Milestones

create or replace function public.tasks_check_links() returns trigger
language plpgsql as $$
begin
  if new.milestone_id is not null then
    if new.goal_id is null or not exists (
      select 1 from public.milestones m where m.id = new.milestone_id and m.goal_id = new.goal_id
    ) then
      raise exception 'milestone does not belong to the given goal';
    end if;
  end if;
  return new;
end $$;
create trigger trg_tasks_links before insert or update on public.tasks
  for each row execute function public.tasks_check_links();

R5. Routine due time:
      anchor 'clock'      -> clock_time + offset

============================================================
9. BUSINESS LOGIC (js/logic/planner.js - pure functions, testable)
============================================================

9.1 Needs Attention (attention.js)
  - Overdue task: due_date < today, status todo/doing.
  - Stale: overdue >= 14 din -> "outdated ho sakta hai, review karo" (auto priority NAHI).
  - Due soon: due within 2 days.
  - Inbox: new items jo 2 din se purane.
  - Goal review due: review_date <= today.

9.2 suggestMainPriority(tasks, today) -> task
  score = urgency + goalBonus + shortBonus
    urgency: due today 100; tomorrow 70; <=3 days 50; <=7 days 25; overdue(<14d) 90; stale 10; no date 0
    goalBonus: +10 agar goal status active
    shortBonus: est <= 30 min => +5 (tie-breaker)
  Highest score. Tie: chhota est_minutes.

9.3 suggestDayTasks(tasks, availableMinutes, today)
  budget = availableMinutes * 0.8   (20% buffer)
  Main priority pehle, phir score order me jab tak sum(est_minutes||30) <= budget.
  Har goal ke liye daily task zaruri nahi.

9.4 Minimum Viable Day
  minimum_day = true => Today screen par: sirf is_must routines + Main Priority + (optional) 1 aur task.
  Reminders me bhi sirf is_must wale routines (tick_logic me is_must filter).

9.5 Water logic
  value += step. status: value >= target => 'done'; value > 0 => 'partial'; value == 0 => row delete.
  Checkpoint reminder: agar abhi ka time checkpoint.at se upar aur value < checkpoint.min.

9.6 Pending task flow (daily review)
  Baad me = scheduled_date = kal. Reschedule = date picker. Split = 2-3 chhote titles daalo.
  Cancel = status cancelled. Isse endless rescheduling nahi hoti.
  Ek task 3 baar reschedule ho to hint: "Ise chhota karo ya cancel karo?" (reschedule_count
  column zaruri nahi - Phase 3; abhi optional).

10. BACKEND API + REMINDER ENGINE
============================================================

10.1 Common (api/_lib)
  admin.js: createClient(SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY, {auth:{persistSession:false}})
  auth.js:
    requireCron(req): header Authorization == 'Bearer ' + CRON_SECRET (crypto.timingSafeEqual). Warna 401.
    requireUser(req): Bearer user JWT -> admin.auth.getUser(token) -> user. Warna 401.
  Sab responses: Cache-Control: no-store. Sirf expected methods allow (else 405).
  Error me internal details client ko nahi.

10.2 POST /api/push/subscribe   (user JWT)
  body {endpoint, keys:{p256dh, auth}, userAgent} -> upsert push_subscriptions (user_id = user.id).
10.3 POST /api/push/unsubscribe (user JWT) body {endpoint} -> delete.
10.4 POST /api/push/test        (user JWT) -> user ke sab subscriptions ko test push.

10.5 POST /api/cron/tick   (cron secret)  <- reminder engine
  For each user_settings where push_enabled:
   1. local = toLocal(now, tz): date (rollover ke saath), nowMin, isoDow.
   2. Agar nowMin quiet hours me: skip user.
   3. Load: day_plan(date), routines(active), routine_logs(date), reminder_sent(date),
      daily_review(date), push_subscriptions. (Kam queries: parallel)
   4. Items banao (tick_logic.js, pure function):
      a) Routine item: applies today? (days_of_week has dow; applies_on vs is_off;
         minimum_day => sirf is_must). dueMin Section 6.R5 se.
         Complete (done/skipped) to skip.
         key = 'routine:<id>'.
      b) Water/checkpoint item: har checkpoint ke liye key 'water:<id>:<at>'.
         Due agar nowMin >= at aur logged value < min.
      c) duty_prompt: agar nowMin >= duty_prompt_time, day_plan me duty_start null aur
         is_off false, aur routines me koi duty_start-anchored hai.
      d) review_prompt: nowMin >= review_time aur daily_review nahi.
   5. Due window: dueMin <= nowMin < dueMin + 90.
      Nudge rule: nudge_no 0 first time; nudge_no 1 tab jab pichla nudge >= 25 min purana.
      Max 2 nudges per item.
   6. Cap: aaj ke distinct batch_id count >= max_reminders_per_day => kuch nahi bhejo.
   7. Due items ko ek hi digest notification me jodo:
        1 item -> title: item ka naam, body: chhota nudge
        2+ items -> title: "N kaam baaki", body: "brush, bath, ..."
      Action buttons: sirf single boolean routine par "Ho gaya"; water par "+250 ml".
   8. Idempotency: pehle reminder_sent rows insert karo (unique constraint,
      on conflict do nothing). Jo rows actually insert hue unhi ke liye push bhejo.
   9. web-push send (urgency 'high', TTL 3600). 404/410 => subscription delete.
      Success => last_ok_at update.
   10. Response: {users, sent, skipped} (koi personal data nahi).

10.6 POST /api/done   (signed token, user JWT nahi)
  Token (notification payload me): {uid, rid, date, act:'done'|'water', exp, sig}
  sig = HMAC_SHA256(DONE_LINK_SECRET, uid|rid|date|act|exp) hex.
  Server: exp check (6 ghante), sig timingSafeEqual, phir service role se:
